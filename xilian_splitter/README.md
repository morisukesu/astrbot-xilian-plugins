# xilian_splitter —— 昔涟的「一句一句说」

把一条长回复切成几段短消息，一段一段发出去。

参考 [nuomicici/astrbot_plugin_splitter](https://github.com/nuomicici/astrbot_plugin_splitter)（对话分段 Pro）的思路重写。
原版很完整，也很重：17KB 的配置 schema、简易 / 进阶 / 专业三种模式、逐段 TTS 合成、
主动发送劫持、会话黑白名单。这台机器上真正用得上的只有一件事——**别一大坨字砸过去**。
所以这版只留下这件事，加上几处昔涟用得上的小心思。

## 它做什么

| 能力 | 说明 |
| --- | --- |
| 先切句、再补切、最后并段 | 按句末标点切细；一句太长时会在逗号处补一刀，仍嫌长就在词与词之间硬切，再合并到合适长度 |
| 保护块 | ``` 代码块、`<think>…</think>`、Markdown 表格内部不下刀 |
| 成对符号 | 「」（）【】《》"" 及其内部一律不切，硬切也会绕开 |
| 图片跟上一段 | 图片、表情、语音这些非文本组件不会跟文字分家，跟着前一段一起发 |
| 拟真延迟 | 段与段之间等 `0.25 秒 + 下一段字数 × 0.055 秒`，封顶 2.5 秒 |
| 第一段带引用 | 上下文更清楚（平台不支持时会被忽略） |
| 和语音配合 | 默认「文字照拆、语音只出一条完整的」：分段喂给 xilian_tts 逐段判语气、拼成一条，所以文字是一句一句的、声音是一个人在说 |
| 尾巴收口 | 最后一段短于 5 字时并回上一段，免得蹦出「好呀♪」这种小碎片 |

## 它怎么发

拦点在 `on_decorating_result`，而且优先级排在**最后**，所以看到的是装饰完的成品。

默认模式（`/分段 语音 full`）：

```
长回复 ──► 切成 N 段文字 ──► 第 1..N 段全部主动发出（段间按字数等待）
                          └─ 整条回复另合成一条语音 ──► 放进 result.chain 交给框架
```

文字全部自己发（最后一段也是），`result.chain` 里只留那条语音 —— 这样框架的 TTS 阶段
扫不到可念的 Plain，就不会再合成第二遍。语音本身在文字发出去的同时就已经在后台合成了，
所以等待是重叠的，不是串起来的。

`seg` / `text` 两种模式仍是老走法，最后一段留给框架：

```
第 1..N-1 段：context.send_message 主动发出
第 N 段：留在 result.chain 里，交给框架正常发送
```

最后一段留给框架是有意的：框架自带的引用、转发消息、文本转图片这些装饰都作用在
最后一段上，插件不和它抢。

## 「一行 6～9 字」这个数是哪来的

不是拍的。翻了这台机器上 AstrBot 消息库（`data/data_v4.db`）里 4 个会话的真人发言，
筛掉系统提示后一共 **71 条**：

| 中位数 | 10 字 |
| --- | --- |
| 25 分位 | 5 字 |
| 75 分位 | 134 字（长尾是整段粘贴的转发） |

按字数分桶：

```
   1-  3 字    14.1%
   4-  6 字    19.7%   ← 峰值
   7-  9 字    14.1%
  10- 12 字    14.1%
  13- 15 字     4.2%
  16- 20 字     2.8%
  21- 50 字     2.8%
  51+   字    28.2%   ← 粘贴的长文本，不是聊天语气
```

**4～12 字占了 62%**，所以把目标定在 8 字一带是有依据的，不是凭感觉。

## 现在的档位

| 项 | 值 |
| --- | --- |
| 起分段门槛 | 25 字 |
| 一段大约 | 8 字（实际落在 6～13 字之间，中位数 9） |
| 单块上限 | 10 字（超过就硬切） |
| 最多段数 | 30 段（约 240 字以内都能保持这个粒度，更长的会自动变粗） |
| 尾巴收口 | 短于 5 字并回上一段 |
| 逗号断点 | 前面至少攒够 6 字才下刀 |

实测：

- 144 字的回复 → **16 段**，每段 `7 / 9 / 8 / 9 / 7 / 9 / 10 / 8 / 7 / 12 / 13 / 7 / 7 / 6 / 12 / 13`，中位数 9
- 576 字的回复 → 30 段（顶到上限），最长一段 25 字

段长偶尔冒出 12、13，是碰上了连逗号都没有的长句，再切就要在词中间下刀了，留着整句更好读。
想更细就 `/分段 段长 6`，代价是语感会变碎。

## 指令

```
/分段                     看当前设置
/分段 开 / 关              开关
/分段 试 <文本>            预览会怎么切——改参数前先用它看一眼
/分段 长度 25              超过这个字数才分段
/分段 段长 8               一段大概多长
/分段 段数 30              最多切几段
/分段 延迟 0.055           每字等多少秒
/分段 范围 private         private / group / all
/分段 引用 开              第一段要不要带引用
/分段 语音 full            开着语音时怎么办：full 一条完整语音（默认）/ seg 每段各一条 / text 不发语音 / skip 不拆
/分段 硬切 开              没有标点的长句要不要在词与词之间断开
```

## 和别的东西的关系

- **框架自带的分段回复**：真正的键是 `platform_settings.segmented_reply.enable`，
  WebUI 里在「配置 → 扩展功能 → 分段回复 → 启用分段回复」。
  这台机器上它是 `false`（默认值也是 `false`），保持关着就好——两个一起开会把同一条回复切两遍。
  顺带一提，框架那套的 `words_count_threshold: 150` 语义是反的：
  **只有短于 150 字的消息才会被它分段**，长回复直接整条发出。所以它管不住你最想拆的那种长回复。
- **xilian_tts**：你这儿的语音是 100% 触发 + 双输出的。默认走 `full`——
  文字照拆，语音只出一条，而且那条语音是按分段语气逐段合成再拼起来的
  （调用 `get_audio_segmented`）。所以既有一句一句的节奏，声音里也听得出她哪句换了气。
  ⚠️ 那边没有 `get_audio_segmented`（换成别的 TTS 了）时，会自动退回「整条读一遍」，
     分段语气就没有了。
  ⚠️ `seg` 模式下合成次数按段数翻倍：一条 16 段的回复就是 15 次合成。
  ⚠️ 整条语音超过 60 秒时，QQ 可能不认（大约 340 字以上）。xilian_tts 的日志里会留警告。
- **xilian_debounce**：不冲突。防抖管「你还没说完」，这里管「她一次说得太多」。
  防抖把话攒好交给模型，模型回完再由这里拆开。

## 出问题时

- 完全没分段：`/分段 状态` 看开关，`/分段 试 <文本>` 看是不是没到门槛（默认 25 字）。
- 切得太多太碎：把 `/分段 段长` 调大（比如 15、25），或 `/分段 段数` 调小。
- 嫌发得慢 / 不想要语音：`/分段 语音 text`（只发文字）。
- 语音太长（超过 60 秒）：把 `/分段 段长` 调大，一段长一点、整体短一点。
- 想回到「每段各配一条语音」：`/分段 语音 seg`。
- 群聊里不生效：默认范围是 `private`，改成 `/分段 范围 all`。
- 改了代码不生效：WebUI 插件面板点「重载插件」。
